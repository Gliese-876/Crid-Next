# Crid Next 需求文档

本文描述 2.0.0 的功能范围与验收口径。实现细节见[技术方案](技术方案.md)，历史设计变更见各版本验证记录。

## 1. Crid Next 简介

Crid Next 延续 Crid 的课表使用场景，以 Kotlin / Jetpack Compose 完全重写。原 Flutter Crid 已归档并保留 Apache-2.0 许可；Crid Next 以 2.0.0 首次公开发布，原创内容的 MIT 适用范围见[许可说明](../LICENSING.md)。两者不保证数据或安装兼容。

应用围绕课表使用场景，提供课表解析与导入、多学期及多方案管理、当日课程查看、周课表浏览、课表导出，以及主题、语言和节假日规则等个性化设置。

## 2. 架构设计

Crid Next 采用 Android 原生架构，技术栈采用 Kotlin 和 Jetpack Compose。最低支持 Android 12（API 31），编译和目标版本均为 API 37；界面适配手机、平板和可调整窗口。

**【建议】**课表解析、课表数据管理、学期与周次计算、节假日处理、界面展示及文件导出应分离。不同导入方式输出统一的数据结构；“今天”“课表”和导出功能复用一致的课程与日期计算规则，避免同一课程在不同界面中出现相互矛盾的结果。

## 3. 主要功能

### 3.1 课表解析、导入与导出

#### 3.1.1 数据概念与课程识别

| 概念 | 定义 |
| --- | --- |
| 学期 | 一段具有起始日、终止日、周数及作息时间安排的教学周期。 |
| 课表方案 | 归属于某一学期的一组课程及授课安排。同一学期可以拥有多个课表方案。 |
| 课程 | 在同一学期、同一课表方案内，以相同课程名识别的课程。教师、地点等其他信息不同，不改变其被视为同一课程的规则。 |
| 授课记录 | 为说明需求而引入的细分概念，指同一课程的一项具体授课安排，用于保留不同周次、时间、地点或教师等信息。该概念不限定数据库实现。 |
| 当前方案 | 当前查看、合并或替换操作所针对的课表方案。是否允许多个方案同时参与展示，见第 3.2.1 节。 |

课程信息应包含课程名、地点、教师及文件中提供的其他重要信息，例如学分。授课安排还应具有足以确定上课时间的周次、星期、节次或具体日期、起止时间等信息。

同名课程被视为同一课程，不等于其所有授课记录均为重复数据。不同授课记录中的时间、地点、教师等差异信息应分别保留，不得仅因课程同名而被覆盖或丢弃。

课程名比较前去除首尾空白、忽略全半角和大小写差异，该规则应在数据规则中统一，避免不同导入方式产生不同的课程识别结果。

#### 3.1.2 已适配格式的解析

应用应稳定解析北京师范大学教务系统导出的课表表格文件，并将解析结果转换为课表方案数据。

北京校区和珠海校区的支持范围应分别通过对应测试用例确认。已适配格式以经确认的样例文件及其预期解析结果为依据，不以“能打开文件”作为解析正确的判断标准。

**【建议】**解析结果应至少区分以下情况：

| 解析结果 | 处理方式 |
| --- | --- |
| 可以完整确定课程及授课安排 | 进入导入确认流程。 |
| 缺少地点、教师、学分等非时间定位信息 | 保留可确定的数据，缺失字段留空并提示，不补造内容。 |
| 明确列出周次，但未安排星期和时间 | 保留为待排时间记录，可导入并在待排入口查看。 |
| 无法确定课程名，或授课时间存在歧义 | 明确指出缺失或歧义，不直接生成看似完整的课表。 |
| 文件损坏、文件类型不支持或模板未适配 | 说明失败原因，并提供重新选择文件的入口；未适配格式可由用户在外部 AI 工具中转为 JSON。 |

#### 3.1.3 导入入口

应用提供“从教务系统导入”和“从本地文件导入”两个入口。

**从教务系统导入：**用户选择北京校区或珠海校区后，在内置 WebView 中打开对应教务系统网站。受支持的 HTTPS 课表下载接入解析和预览；也可先在其他浏览器保存文件，再从本地导入。

**从本地文件导入：**用户选择本地文件后进入解析流程。文件来源包括在其他设备或浏览器中下载的教务系统课表，以及 Crid Next 导出的可重新导入文件。

此外，也可通过系统分享路径“分享至 Crid Next”导入课表文件。

#### 3.1.4 导入目标与写入方式

导入时，用户应能够选择目标学期，并选择以下一种处理方式：

| 方式 | 行为 | 影响范围 |
| --- | --- | --- |
| 新建课表方案 | 将导入内容保存为目标学期下的新方案。 | 不覆盖已有方案。 |
| 合并到当前方案 | 将导入内容加入选定的当前方案。 | 保留原有课程及授课记录；重复、冲突数据的处理规则见下文。 |
| 替换当前方案 | 用导入内容替换选定方案的课表内容。 | 不应扩大为替换整个学期或其他方案。 |

**【建议】**统一导入流程为：获取文件 → 解析 → 选择目标学期与写入方式 → 预览结果及影响范围 → 用户确认 → 保存。

**【建议】**导入确认与异常处理遵循以下规则：

- 预览显示目标学期、目标方案、课程及授课记录数量，以及缺失字段、重复项和冲突项。替换操作应明确说明哪些原有内容会被替换。
- 合并时，相同课程名按同一课程归类。仅在周次、星期、起止节次、具体日期、起止时间、地点、教师、备注及待排状态均一致时去重；周次先排序去重。差异授课记录分别保留，学分与附加信息的差异也保留。
- 当文件中的学期、周次或节次与目标学期及作息不一致时，提示差异并要求处理，不自动截断超出范围的内容，也不擅自改写目标学期。
- 用户取消导入、解析失败或保存失败时，不改变已有方案；保存操作应避免形成只写入部分记录的中间状态。

#### 3.1.5 未适配格式的外部转换

内置 BYOK 解析及 API 密钥配置已在 1.15.0 移除。用户可将 [README 中的提示词](../README.md)、[JSON 示例](../examples/timetable.json)和自己的课表交给所选 AI 工具，转换后从本地文件导入。

生成文件须遵守版本化 JSON 结构，保留源课程及不同授课安排，不猜补缺失信息。导入仍执行结构与业务校验，并由用户核对预览；结构有效不代表模型已正确理解原课表。外部工具的文件上传由用户自行操作，应用不会因本地解析失败自动上传课表。

#### 3.1.6 可视化导出

应用应支持将课表导出为 PNG 图片或 PDF 文档，并采用经过美化和调优的自动排版。PNG 和 PDF 文件的排版须保持一致，PDF 无需规范化到标准纸张类型（如 A4）。

| 可配置项 | 要求 |
| --- | --- |
| 导出视图 | 支持日、周、月、学期视图。 |
| 导出范围 | 支持按日期、周、月或学期选择内容范围。 |
| 导出格式 | 支持 PNG、PDF。 |
| 导出路径 | 允许用户选择具有写入权限的目标位置。 |
| 导出分辨率 | 仅对 PNG 提供分辨率设置。 |

“视图”决定内容的排版组织方式，也决定范围选择器的单位：日视图选择日期、周视图选择教学周、月视图选择月份，学期视图选择学期及其方案。

日、月和学期视图属于原文明确要求的导出能力；它们不自动意味着应用内“课表”页面也必须增加对应浏览模式。

**【建议】**自动排版的验收口径包括：课程文本不相互遮挡，长课程名能够合理换行，日期和周次标识清晰，课程颜色和状态含义与应用内一致。不能通过无限缩小字号来容纳过多内容。

每个选中日、周、月或学期生成一页；PDF 合并为多页文件，PNG 每页输出一个文件。导出前展示预计页数或文件数。图表与当前视图样式同步，页首汇总待排数量，页底不附课程列表；完整源记录通过 JSON 导出。

#### 3.1.7 可重新导入的数据导出

除 PNG 和 PDF 外，应用还应支持导出可被 Crid Next 重新导入的数据文件。此类文件与面向查看、打印的可视化文件属于不同导出类型。

可重新导入文件包仅包含课程方案信息，不包括学期信息，并包含格式版本标识；不包含 API 密钥等敏感设置。

**【建议】**对应用自身支持的同一格式版本，导出后重新导入应恢复等价的课表内容。所谓等价，是指课程身份、授课安排及必要配置保持一致，不要求文件字节或数据库内部标识完全一致。

重新导入时仍应允许用户选择目标学期，以及新建、合并或替换方案。

### 3.2 界面交互

#### 3.2.1 底部导航与页面职责

导航包含“今天”“课表”“方案”“设置”四个入口。手机使用底部导航，窗口宽度达到 600 dp 时改用侧栏，达到 840 dp 时展开侧栏文字。

| 页面 | 主要职责 |
| --- | --- |
| 今天 | 展示当日课程信息，包括课程名、授课时间、地点、教师及其他重要信息。 |
| 课表 | 默认以周视图展示本周课程，并允许通过页面交互切换到不同周。 |
| 方案 | 创建不同学期，并在同一学期下管理、选择多个课表方案。 |
| 设置 | 配置主题、语言、一周起始日、法定节假日、调休及非本周课程显示等选项。 |

当前学期与方案统一在“方案”页选择，“今天”和“课表”读取同一选中方案。无学期、无方案、当日无课及当前周无课分别提供空状态。

课程方案采用“多个方案可保存和切换、同一时刻选定一个展示方案”的规则，不叠加显示。

#### 3.2.2 学期日期与周数

创建学期时，提供起始日、终止日和周数三个字段。用户手动设置学期时，至少提供两个字段，由系统推算第三个字段；使用预填默认值的情况见第 3.2.4 节。

**基本校验：**起始日不得晚于终止日；周数应为正整数。界面应区分用户手动输入与系统推算的值。

设起始日为 `S`，终止日为 `E`，周数为 `W`。日期间隔均按自然日计算，并包含起止两日。

| 已知字段 | 推算规则 |
| --- | --- |
| 起始日与终止日 | `W = (E - S + 1) / 7`，日期须构成完整自然周。 |
| 起始日与周数 | `E = S + (7 × W - 1) 天`，直接使用计算结果作为终止日。 |
| 终止日与周数 | `S = E - (7 × W - 1) 天`，直接使用计算结果作为起始日。 |

新建与编辑学期遵循当前“一周起始日”设置：周一模式从周一至周日，周日模式从周日至周六，日期范围恰好包含 `7 × W` 天。旧有未对齐学期可读取；编辑时保留原值并提示调整，打开或取消不会改写。

当字段彼此矛盾时，优先遵循用户最后手动填写或修改的字段。

字段冲突时保留最近两次手动输入对应的两个字段，重新计算剩余字段；系统自动回填不更新字段的手动编辑顺序，也不连锁触发其他字段的再次推算。用户尚未提供两个有效字段时，不保存自定义学期。

**【建议】**修改“一周起始日”设置不应静默改写已保存学期的起止日期或周数。

“第 1 教学周”按自然周边界划分。

#### 3.2.3 作息时间

创建学期时，用户应能够选择作息时间安排。作息安排至少包含每天的课节数量，以及每节课的开始时间和结束时间。

**【建议】**作息数据中的节次编号应连续，每节课开始时间早于结束时间，并避免未经说明的课节时间重叠。解析得到的节次应能够映射到所选作息；无法映射时在导入确认界面提示。

#### 3.2.4 默认学期

用户未自行指定时，以北京师范大学发布的 **2026 年秋季学期安排及学校作息**作为默认值。

**【建议】**将默认值作为创建学期时的预填模板，允许用户直接确认，也允许修改。

#### 3.2.5 设置项与默认值

| 设置项 | 可选值 | 默认值及显示规则 |
| --- | --- | --- |
| 主题 | 跟随系统、浅色模式、深色模式 | 默认跟随系统。 |
| 语言 | 跟随系统、简体中文、繁体中文、English | 默认跟随系统。系统语言不属于支持范围时，禁用“跟随系统”并回退至 English。 |
| 一周起始日 | 周一、周日 | 默认周一。 |
| 法定节假日 | 启用、禁用 | 默认启用。 |
| 调休 | 启用、启用且不补班（补课）、禁用 | 仅在启用法定节假日时显示；默认“启用且不补班（补课）”。 |
| 显示非本周课程 | 启用、禁用 | 默认启用。 |

用户明确选择简体中文、繁体中文或 English 后，不受“跟随系统”的语言回退条件影响。

非本周课程指属于当前展示方案、但授课周次不包含正在查看周的记录。该选项影响周课表及相应导出，不会把非本周课程变为实际授课课程；“今天”仅显示当天实际课程。

另有上课前提醒、提前分钟数与闹钟级提醒设置。提醒默认关闭，默认提前 15 分钟；闹钟级模式默认关闭。送达条件见[提醒送达设计](提醒送达设计.md)。

#### 3.2.6 法定节假日与调休

法定节假日和调休配置共同决定课程在特定日期是否按休假或补课规则处理。

| 法定节假日 | 调休模式 | 休假处理 | 补班／补课处理 |
| --- | --- | --- | --- |
| 禁用 | 不显示、不生效 | 不应用额外的法定假日及调休休假规则，按原课表处理。 | 不应用调休补课规则。 |
| 启用 | 禁用 | 仅按法定节假日休假。 | 不安排调休补课。 |
| 启用 | 启用且不补班（补课） | 法定假日休假，并应用公告中的额外调休放假。 | 不新增调休补课；这是默认模式。 |
| 启用 | 启用 | 法定假日休假，并应用公告中的额外调休放假。 | 按已确认的教学映射在对应日期补课。 |

启用调休时，以相应年度官方公告为依据；应用需要区分法定假日本身、调休增加的休假日和补班／补课日，不能将三者混为一个日期状态。

**【建议】**节假日设置改变课程的有效状态和展示，不删除底层授课记录。休假课程保留时，应清楚标注不上课，不能以普通课程样式误导用户。

**【建议】**“不补课”仅表示不根据调休规则新增补课，不应删除原课表中本来就存在的周六、周日课程。

先预存 2026 年的调休数据，并在每次启动时静默尝试联网刷新（成功或失败均不提示），只在设置中的调休选项中显示最新同步时间。如果数据已过期，在设置界面提示。

### 3.3 UI 设计

#### 3.3.1 设计方向与原生实现

整体界面应简约、清晰、具有现代感，并积极使用 Android 原生控件和标准实现。

采用 **Neural Expressive** 的设计目标，以 Google 正式发布的 Neural Expressive 资料及 Gemini 的官方公开界面与交互示例作为参考。

设计参考限于 Gemini 的色彩、排版与运动方向；实际组件采用 Jetpack Compose Material 3，不将该参考视为 Android 平台的组件规范。

**【建议】**将设计参考转化为本项目可评审的视觉规范：明确课程磁贴、导航、按钮、弹层和状态反馈的色彩、排版及动效表现；触觉反馈的使用场景另行确认。这些是面向 Crid Next 的落地建议，不是 Google 已发布的 Neural Expressive 组件规范。原有的磁贴布局、课程颜色身份和无障碍要求继续以第 3.3.2—3.3.4 节为准，不因参考 Gemini 而改变页面职责或新增语音对话等功能。

**【建议】**对项目支持的系统版本，优先采用可用的原生标准实现；新组件或视觉效果无法使用时提供一致的替代方案。

#### 3.3.2 磁贴布局与时间比例

“今天”和“课表”均采用课程卡片。卡片高度结合时长与文字可读性确定，同一视图内较长课程保持更高；短课使用平滑的可读高度下限，不要求所有时长严格线性。

| 维度 | 已确认规则 |
| --- | --- |
| 课程磁贴高度 | 以 Softplus 曲线结合时长与可读下限，必要时按文字高度和时间轴对齐约束增高，并保持展示跨度的时长顺序。 |
| 课间显示 | 周课表压缩无课空档；今天页采用单列日程，卡片之间不按空闲时长留白。连续课程卡的跨度包含内部课间。 |
| 时间轴覆盖范围 | 时间轴无需从 00:00 连续展示到 24:00，可以只覆盖课表需要展示的时段。缩减时间轴范围不得截断或遗漏当前视图应展示的课程。 |
| 真实时间与顺序 | 无论课间如何压缩、时间轴覆盖多少小时，都应保留准确的课程起止时间和可理解的先后关系；显示压缩不改变课程数据，也不能将压缩后的视觉距离当作真实经过的分钟数。 |

例如，同一视图内 90 分钟课程高于 45 分钟课程，但为保证短课文字可读，高度不必恰好为两倍。具体曲线与对齐规则见[技术方案](技术方案.md)。

课程名作为主要信息，地点与教师依次展示。周课表空间不足时可省略次级信息，详情保留完整内容；同一位置的记录以分组入口展示。今天页为每张卡保留完整文字所需高度。时间放在左侧，其他字段为空时不显示空字段。

连堂课程包含内部课间时，合并展示，对应磁贴的课程时长为起止时间跨度。

#### 3.3.3 课程颜色与状态区分

每门课程应具有唯一的课程色或课程色系；为适配不同状态或主题，必要时可以使用同一色系中的不同颜色。

在同一学期、同一方案内，同名课程使用同一课程颜色或色系，即使其教师、地点等信息不同。不同授课记录仍按第 3.1.1 节保留各自内容。

| 状态 | 视觉要求 |
| --- | --- |
| 正常课程 | 使用正常课程颜色和磁贴样式。 |
| 非本周课程 | 在启用显示时，使用更淡的课程色填充与彩色虚线边框。 |
| 法定节假日或调休休假时段 | 启用相关规则时，在课表中为休假时段添加阴影，同时用色彩变化区分受影响课程与正常课程。 |
| 调休补课 | 不使用休假阴影 |

**【建议】**一个课程同时具有“非本周”和“休假”等状态时，保留各状态标识，不因叠加阴影而丢失虚线边框或重要文字。主题切换与页面切换不应造成同一课程颜色身份随机变化。

#### 3.3.4 无障碍与动效

配色应遵循无障碍设计规范，并对色盲用户友好。课程状态不能仅依靠颜色表达，应结合边框、文字或其他可辨识标记。

动效应流畅、自然，符合物理直觉，并帮助用户理解页面切换、内容展开和状态变化，不能妨碍查看或操作课程。

**【建议】**在浅色、深色主题和常见色觉差异模拟下检查主要界面；对大字号和减少动画的系统设置提供适配。

## 4. 其他要求

### 4.1 性能取舍

应用预期运行在性能较高的现代设备上，允许在有明确体验收益的前提下，采用以空间换时间或增加一定性能开销的实现方式。

在达到相同功能与视觉效果时，仍应尽可能优化算法和实现，降低处理时间、内存占用及其他设备开销。重点关注课表加载、程序化课表解析和高分辨率图片导出。

**【建议】**对缓存、预计算和复杂动效等方案，应比较实际体验收益与资源成本。耗时解析和导出过程中，界面应保持可响应，并显示处理状态；不能仅因目标设备性能较高而忽略长时间阻塞或不受控的内存增长。

### 4.2 其他功能

提供自适应应用图标、可设置主题且随尺寸调整的小组件，以及分别使用不同图标的今天、课表与导入快捷方式。后台采用系统周期任务维护课表状态，课程提醒独立由 AlarmManager 调度，遵循 Android 权限和后台限制。

此外，在必要范围内尽可能支持新的 Android 特性。
